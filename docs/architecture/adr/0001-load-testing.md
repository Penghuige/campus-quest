# ADR 0001: 压测怎么做——容量估算先行、场景即代码、正确性断言为中心

日期: 2026-10-30 · 状态: 已接受（owner 批准 2026-10-29 设计 + 2026-10-30 执行）
背景: docs/superpowers/specs/2026-10-29-load-testing-design.md ·
报告: docs/loadtest/capacity-report-2026-10.md

## 决策

1. **容量估算先行**：目标数字从真实校园规模推导（学校 → 大课 → 拖延分布 →
   并发），不抄技术指标。这是系统设计面试的标准起手式，也是目标合理性的来源。
2. **场景即代码**：locust 场景（S1 截止抢交 / S2 开抢名额 / S3 读基线）参数化进
   `backend/loadtest/`，随产品演进复跑；不是一次性脚本。
3. **正确性断言是中心**：压测的价值不止延迟数字——check_s1/check_s2 在负载后
   直接断言数据库层面的保证（零丢失/零重复/§9.3 分档 oracle/无超发），
   把仓库一贯的并发纪律变成"负载下依然成立"的证据。
4. **429 与业务性 4xx 独立分类**：自家限流器的 429 与业务拒绝（在途冲突、
   截止后、名额尽）是合法结局，绝不混入错误率——否则所有头条数字都是谎言。
5. **登录离线铸 token**：与登录同一 `issue_session` 代码路径、不经 HTTP，
   每 IP 登录限流因此天然不可见（报告如实声明"登录容量未测"）。
6. **真实文件、共享池**：CSV/XLSX/SQLITE 真实可解析（验证管线会真解析）；
   单 gevent 进程内共享每族一件（按档位中位数），逐用户生成会把"我们的 CPU"
   混进被测系统。

## 被否决的替代

- **一次性脚本+截图**：不可复跑、不可回归，面试讲不出方法。
- **测登录路径**：单源 IP 必然撞限流，测出来的是自家门卫不是系统。
- **分布式加压**：单机形态下的诚实数字 > 假装多机；报告写明单机。
- **逐用户独立文件**：gevent 单进程内会串行化在生成器上。
