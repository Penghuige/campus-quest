# §5.6 契约修订：refresh 轮换的稳定后继者重放窗（PR #10，已合并）

> 状态：**已实施（代码已随 PR #10 于 2026-09-30 合并；休眠能力待部署侧启用）——合并本修订只落代码，不改任何运行行为**。
> 默认 `REFRESH_GRACE_SECONDS=0` 保持 §5.6 原语义
> （`Login -> A; A -> B; reuse A must fail`）不变。
> **启用（部署侧设 `REFRESH_GRACE_SECONDS>0` 并提供专用密钥）= 裁定生效**；
> 这是独立的、显式的 owner 决策，与是否合并本代码无耦合。

## 动机（测试缺陷 #1）

内存态 access token + 轮换式 refresh cookie 的组合下，任何"同一 refresh
token 的并发呈现"（多标签冷启动、跨端口预览共罐、非浏览器客户端）
都会产生输家：赢家轮换消耗旧 token，输家 401 被渲染成未登录。
浏览器同源多标签由前端 Web Locks + BroadcastChannel 收养层（PR #14）串行化；
本修订覆盖**锁够不到的场景**（跨源、脚本、未来移动端）。

## 配置硬界（第三轮 review 落地）

- `REFRESH_GRACE_SECONDS` 只允许 **0..60**（config 加载即校验，负值/超界
  fail-closed——该窗口改变 bearer 重放授权，不能靠"运维自觉设 30"）；
- 启用窗口时必须提供结构合法的专用密钥，否则拒绝加载。

## 新语义（稳定后继者）

在窗内（默认建议 30s）重放被退役 token：

- **不再轮换**——沿退役行上的加密 envelope 链解析到**当前存活代际**，
  原样重发该代际的 refresh secret，并铸造绑定同一存活会话行的新
  access token；
- **收敛不变量**：N 个并发呈现方最终持有**同一个**存活 refresh 代际
  （旧行为的"再轮换尖端"会让先到者的 access/cookie 立即失效——
  `find_with_live_session` 要求 `replaced_by IS NULL`——被 review
  判为 P0 否决）；
- 登出吊销的谱系**永不**经重放复活（解析中检查存活行状态）；
- 呈现凭证自身过期先于任何宽限逻辑判定；
- 窗外重放维持 §5.6 原样拒绝。

## 登出语义同步修订

`revoke_session` 从"撤销呈现行"改为"沿 replaced_by 链撤销**存活尖端**"：
持有陈旧代际的登出（竞态后 cookie 罐的常态）不得成为 no-op 而留存活
会话。并发 `refresh ↔ logout` 的终态必须是**零存活会话**。

## 安全权衡（记录在案）

- envelope = 后继者 refresh secret 的 Fernet 密文（`replay:v1:` 域前缀，
  **专用 `REFRESH_REPLAY_ENCRYPTION_KEY`**——刻意不复用 TOTP 密钥，
  任一密钥轮换/泄露不影响另一密文；配置加载时校验结构合法性），
  仅存于退役行、仅窗内可读、绝不入日志/DTO；
- 窗内持有被退役 token 者可获得当前存活代际——这是本设计的**有意
  交换**（BCP 惯例：短窗一次性重发优于把合法并发方踢出登录）；
- 窗外重放**不自动吊销会话族**：陈旧标签页与盗用不可区分，误报
  代价（登出其他标签）大于收益；如需更严可后续加族吊销，独立裁定。

## 验收（已在本 PR 落实）

- 服务层：重放返回与原轮换**相同**的 refresh token；存活行不被
  窗内重放退役；N 次重放零新增会话行；logout(陈旧代际) → 零存活。
- HTTP 层：双客户端乱序冷启动 → 两个 access token 均可用 → 窗过期后
  终态 cookie 仍可刷新 → 陈旧代际登出后零存活、/me 401。
