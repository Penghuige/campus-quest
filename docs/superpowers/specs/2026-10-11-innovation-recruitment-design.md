## 1. 本轮目的、依据与边界

让已经开通负责人资格的学生，针对自己有管理权限的项目发布岗位，让校内浏览者找到实践机会并通过授权渠道自行联系。尚无成果、尚未组队的创意项目也能招募。

依据工作区《华师令创新创业板块独立需求说明书.docx》v0.7 的 PR-03/04/05/07/08/09/10/11/12/14、AC-01 与 UI-02/03，以及 `docs/handovers/2026-10-10-innovation-roadmap.md` 的 R3。2026-10-11 已直接读取原 DOCX 相关段落，并与技术文档 §7.1/7.3/9.2/17.1 对照。

已有用户决定继续有效：

- 发布须同时具备负责人资格和对应项目权限；招募独立免审，不依赖已有审核成果。技术参考中“资格或管理权限”的表述不能替代用户要求的“资格且项目权限”。
- 招募更新免审；成果内容更新仍走 R2 全复审。招募发布不能替换成果公开版本。
- 学校统一身份认证最后接入；本轮使用现有真实演示会话和明确标注的模拟资料，不称为已经完成学校认证。
- 不重置开发数据，不修改 main，不自动合并；沿用 `codex/innovation-platform`，PR #43 保持 Draft。
- 默认 Sol High，不声称主聊天自动切换。需要独立评审时，在该任务开始前另行说明实际模型。

本轮交付岗位草稿、发布/更新、关闭/重新开放、截止与提醒、授权联系，以及项目库的基础浏览、筛选和分页。共同管理/成员挂名/转让属于 R6；完整举报治理属于 R7；不加入站内投递、报名、简历、录取、私聊、积分奖励、人才库或导师库。

## 3. 岗位内容与发布授权

每项目可有多条岗位；岗位属于项目，不是 Task 或 Assignment。本人可保存不完整草稿，发布/重新开放/发布更新必须完成服务端校验。

| 内容 | 发布规则 |
| --- | --- |
| 项目名称、方向、阶段说明 | 必填；名称可从已保存项目草稿载入，发布前预览确认；后续独立保存项目不自动改公开招募 |
| 项目基础介绍 | 必填，仅描述目标、方向和工作计划；不提供成果、奖项、证明上传或团队成员挂名字段 |
| 是否创意起步 | 显式选择；选择后公开标注“创意起步”，必填目标与初步方案；现有自由文本阶段不被批量改写 |
| 岗位、人数 | 必填；人数为整数 1～999，岗位名称最多 120 字符 |
| 职责、能力要求、投入时间 | 必填；分别最多 2000、2000、500 字符；允许能力要求写“无需经验，愿意学习” |
| 是否接受零基础 | 必填布尔值；两种选择都明确展示，不用颜色代替文字 |
| 截止日期 | 可空；有值必须为未来 UTC instant，界面明确展示业务时区与具体时间 |
| 联系渠道 | 微信、QQ、邮箱、手机号中至少一个明确选中且有效的值；不读取账号绑定联系资料作为默认公开渠道 |

项目基础介绍最多 2000 字符，创意目标和初步方案各最多 2000 字符；名称最多 120、方向最多 120、阶段说明最多 80。用户文本按纯文本处理。微信/QQ 使用有界标识字符串，邮箱/手机号按现有校验能力规范化；联系方式不作为任意 URL 执行，不生成脚本协议链接。

R3 当前可操作范围只有项目本人负责人，因为共同管理员尚未实现。运营身份、普通学生身份、Teacher/Admin 身份均不自动获得他人的岗位管理权。

发布、更新、重新开放在事务内重新验证 ACTIVE 学生账号、已开通资格、项目归属、保存版本与岗位内容。资格不足仍能维护私有草稿和关闭自己的已有招募，不能发布或重新开放。被暂停账号不能进行业务写入。公开招募查询也排除账号失效或资格失效的发布者，避免仅在发布时检查。

“免审”指没有运营预审，不代表内容已经核实。公开页注明“招募信息由负责人发布，未经成果核实”。自由文本不可能由字段结构证明事实真伪；禁止虚构成果的填写说明与后续举报治理不能被描述为已经自动核验。

## 4. 保存与公开版本

保存草稿和发布分开。首次发布生成固定的岗位公开版本；已发布岗位修改后先保存草稿，再点击“发布招募更新”，免审切换公开版本。待发布的修改保持私有，不显示给浏览者。

公开版本只包含本次明确确认的项目基础介绍、岗位和选中联系渠道。任何查询都不序列化 `ProjectDraft`、负责人四项资料、成果草稿、待审快照或证据实体。成果区域复用 R2 的已通过投影，单独显示核实状态和对应版本的项目信息。

招募的项目介绍与成果随附介绍可能来自不同时间：界面分别标记“负责人发布的招募介绍”和“随该成果核实的项目信息”。招募名称或介绍更新不改变成果的原名称、原描述或原公开指针。不能以整个项目一枚“已审核”标识覆盖免审岗位。

发布确认展示将公开的基础介绍、岗位和联系渠道，解释可见人群；保存不等于同意公开。R3 不添加招募附件或作品上传，避免用招募绕过证明访问与成果审核。

## 5. 生命周期与时间

持久状态为 `DRAFT / OPEN / CLOSED / EXPIRED`，另有独立 `NORMAL / TAKEN_DOWN` 治理状态。R3 只实现治理状态的可见性约束，不提供完整举报、下架/恢复工作台，也不宣称 R7 已交付。

- `DRAFT → OPEN`：首次发布；填全字段并明确授权联系。
- `OPEN → OPEN`：显式发布更新；保存草稿不切换公开版本，也不算确认继续招募。
- `OPEN → CLOSED`：本人关闭，立即阻止校内列表、详情、联系读取；保留本人维护记录。关闭不隐藏已审核成果。
- 有截止日期且 `now >= deadline_at`：逻辑立即为过期，列表/详情/联系拒绝返回有效招募，Worker 随后落库为 `EXPIRED`。Worker 停止不会延长截止时间。
- `CLOSED / EXPIRED → OPEN`：显式重新开放，重新校验版本、资格、联系与未来截止时间；开始新的招募周期。
- 已下架岗位不能通过发布更新、确认继续或重新开放恢复。未来 R7 恢复必须另走治理动作。

公开列表只含当前有效 OPEN 岗位。关闭、到期、下架岗位的普通用户直链返回 404；本人在管理页仍可看到具体状态。项目若仍有已公开成果，继续可浏览成果；仅有一条招募的项目在岗位结束后不再出现在校内项目列表。

所有业务时间来自可注入 Clock，以 timezone-aware UTC 保存。截止瞬间前/恰好/后均有测试，浏览器倒计时只辅助展示。

无日期岗位发布/重新开放时设置 `last_confirmed_at=now`、`next_remind_at=now+30天`。这里的 30 天是 30×24 小时的持续时间，不是月底或自然月规则。

“确认继续招募”只允许无截止日期的有效岗位；显式操作重置提醒起点。修改简介、发布普通招募更新不会默认为确认。由有日期切换到无日期的显式发布更新开始 30 天周期；切换为有日期则清除提醒计划。

未确认不自动关闭。每到 30 天周期产生一条提醒并推进下周期；调度停机跨过多个周期时只补一条提醒，推进到原周期序列中的下一未来时刻，避免恢复时轰炸用户。确认继续或重新开放建立新周期标识，旧周期任务不能推进或关闭新周期。

## 6. 联系方式的独立授权与读取

R3 联系授权按岗位保存，不提前做全平台联系方式管理器。每种渠道最多一个值；岗位发布版本只能引用该岗位归属下、本次明确授权的渠道。不能引用他人或其他项目的联系记录。

列表、搜索和普通详情只返回“可查看联系方式”及所选渠道种类，不返回值。浏览者主动点击“查看联系方式”后才调用单独接口；响应 `private, no-store`，按每次请求的当前身份和岗位有效性重新校验，不做跨用户共享缓存。

只有这次独立授权读取可向校内浏览者披露自选微信、QQ、邮箱、手机号。它是 PR-09/10 对通用禁止展示联系信息规则的明确业务例外；学号、账号绑定联系资料、其他未选渠道仍不能进入普通响应/DOM。未点击前浏览器网络响应及 DOM 均无渠道值。

联系值由输入者保证为本人或已经取得使用同意的项目联系渠道，发布确认明确这一责任；不宣称系统已经核验第三方渠道持有人同意。

本人可立即撤销已公开渠道，独立于待发布草稿。剩余渠道至少一项时原子撤销该渠道；撤销最后一项必须明确确认“同时关闭招募”，否则 409 并保持原状态。操作同时更新公开授权、版本、审计；重新开放须重新选择并确认有效渠道。已公开过的值无法从浏览者记忆或其自行复制记录中收回，系统保证撤销后的新请求不可获取。

联系读取使用现有 Redis 限流基础设施，按账号设置 30 次/分钟的有界窗口；限流依赖失效返回安全错误而非不受限披露。敏感读取写持久脱敏审计后才返回，审计失败不披露。审计仅记 actor/资源/版本/渠道类型/时间/request_id，不保存渠道值、项目正文或材料内容。联系值不进入普通日志、事件 payload 或通知正文。

## 7. 后端、任务与通知组合

保持模块化单体：薄 router → 招募服务/公开查询/提醒服务 → PostgreSQL、现有审计与 NotificationPort。使用独立招募模型、schemas、service/router；不把这一闭环塞进成果审核服务。

数据库保存岗位私有草稿、不可变公开版本、当前公开指针、联系授权、周期计划和操作回执。显式外键连接项目与岗位；版本、人数、状态及当前公开版本归属有约束；建立项目岗位、有效列表、截止和提醒扫描索引。迁移不改已共享的历史迁移，不自动发布已有项目或填造联系资料。

所有 mutation 带保存版本；创建与状态动作携带稳定 `request_id`，复用项目既有规范，不另要求 Idempotency-Key header。动作回执以岗位/请求唯一键及归一化载荷摘要去重；同 key 不同载荷 409。重放先检查当前访问权限，返回已执行操作回执与当前状态，不让旧发布/重新开放/关闭请求作用于新周期。

锁顺序沿用用户/资格 → 项目 → 岗位 → 该岗位的联系与周期记录。Worker 不在已持岗位锁后反向取得用户锁；重新锁定后重读状态和版本，不能根据扫描时旧数据关闭刚延长的岗位。发布公开指针、授权记录和审计同事务成功或回滚。提醒周期推进与通知 intent 同事务持久化。

提醒事件建议为 `IE_RECRUITMENT_CONFIRMATION_DUE`，首期仅站内通知，明确修改事件契约/数据库 CHECK/默认模板和该事件渠道策略；不会因现有 critical-event 默认扇出而额外发送短信或邮件。既有 Task、成果和安全事件的渠道语义保持原样。

周期事件 key 含岗位、周期标识、到期 instant；通知/投递的现有数据库唯一键继续去重。正文只含岗位名称、确认提示和本人管理路径，不含联系方式。通知在 Worker 完成真实站内投递后才视为可见；不能直接伪造 SENT 或改松通知页过滤。

沿用通知模块注入 resolver 的模式，在投递时重新判断岗位已关闭/有截止日期/旧周期等情况，跳过尚未投递的过时提醒。现有通知不反向依赖创新创业 ORM；缺少本事件 resolver 的生产组合 fail closed，不安装空适配器。

截止/提醒扫描须注册真实 Celery task 和 Beat schedule，使用项目 worker session factory、有界 batch、可配置扫描周期。生产组合和 CI 烟测覆盖注册、调度、PG/Redis、intent→投递→通知页读取。开发启动方式补上本项目所用 Worker/Beat 与归属检查、隐藏启动、日志和停机入口；端口/数据不重置，不能为了演示真实 30 天规则而更改开发业务时钟。

## 8. API、页面与后续 UI 修改

接口沿用 `/api/v1/ie`：

| 接口范围 | 用途 |
| --- | --- |
| `/me/project-drafts/{project_id}/recruitments` | 本人创建、分页列表；单条草稿读取/更新 |
| `/me/project-drafts/{project_id}/recruitments/{id}/publish` | 初次发布、免审发布更新；只取保存内容与版本 |
| 同单条路径下 `/close`、`/reopen`、`/confirm-active`、`/revoke-contact` | 显式动作、版本检查与稳定请求去重 |
| `/projects`、`/projects/{id}` | 校内项目聚合查询，只读成果通过版本和有效岗位公开版本 |
| `/recruitments`、`/recruitments/{id}`、`/recruitments/{id}/contacts` | 有效岗位分页、详情和单独联系读取 |

创建响应 201，原请求重放 200；缺权限 403，非本人资源/不可见资源 404，版本/状态/请求冲突 409，字段无效 422，限流 429。错误按稳定 code 和 kind 映射，不解析中文正文。API 面改变时同步提交 OpenAPI 快照及生成类型。

校内入口在 `/innovation` 成果区域之后加入“正在招募”。项目库指向 `/innovation/projects`，原 `/innovation/achievements` 和成果直链保留。项目详情将成果与岗位分区；有成果不保证岗位已经审核，仅有招募的项目显示“暂无已核实成果”。

项目/招募列表分页，支持有界关键字、方向/阶段说明、是否正在招募、是否接受零基础；筛选作用于公开投影，不能搜索私有草稿。详情加载岗位与成果避免逐行 N+1 查询，内容较多时按区分页。项目摘要优先取最近通过成果的项目介绍；没有可见成果时取最近有效岗位的介绍，并明确来源。详情保留每份成果的原快照，不拼装成一个新“已核实项目版本”。

本人从“我的项目”进入项目下的“成果管理／招募管理”。既有“项目草稿”文案改为能容纳草稿和已发布内容的“我的项目”；私有编辑区仍说明保存不会自动公开。管理页有清楚的发布预览、状态、草稿修改提示、联系撤销、关闭/重新开放，以及无日期岗位的“确认继续招募”。

6. 有日期招募到点即停止可见；无日期招募显示下次提醒时间，确认继续后重新计算。30 天完整周期在专用测试世界以 Clock 验证，开发演示不必等待 30 天，不伪造开发通知。
