# 创新创业第一步：本人项目草稿

依据：工作区《华师令创新创业板块独立需求说明书》v0.7 §4、§7、§8，以及技术实现文档 V1.1。原需求高于技术建议。用户已授权继续开发，由 Agent 执行命令与验证，用户体验成果并学习关键概念。

## 本轮交付与边界

完成一个可用闭环：登录学生进入个人项目管理，新建私有草稿，保存至真实 PostgreSQL，刷新后读取、编辑并再次保存。项目与原 Task 分属不同业务域。

本轮仅是私人准备区。现有 ACTIVE/STUDENT 身份可准备自己的草稿，不代表获得项目负责人资格、学校统一认证或公开发布权限。负责人四项资料及开通操作依原需求另行实现；正式发布前必须接入资格检查。此次没有公开项目列表、发布接口、成果审核、招募、附件、奖励或身份资料收集。成果草稿放到下一小步，避免把成果内容混入项目概况。

草稿只保存项目概况：名称、简介、方向、阶段、团队现状。阶段是负责人填写的文本，与获奖情况无关。仅名称非空；其余字段允许未完成，不套用正式发布校验。实施长度上限：名称120、简介2000、方向120、阶段80、团队现状1000字符；全部去除首尾空白。限制由后端与前端共同说明。

## 服务与数据契约

- 独立 `innovation` 模块，模型、输入/输出 DTO、服务及薄路由；共用已有 Actor、会话、CSRF、错误信封、Clock、数据库会话。
- 新表 `ie_project_drafts`：UUID 主键、owner_user_id 外键、creation_request_id、不可变首次规范化请求的 SHA-256 指纹、五个内容字段、version、created_at、updated_at；时间 UTC，owner+更新时间索引，owner+creation_request_id 唯一约束，长度/版本约束。迁移 0025 只新增，不修改已发布历史。
- 本人管理接口置于 `/api/v1/ie/me/project-drafts`。列表分页且仅本人；创建、管理详情和更新均校验 ACTIVE/STUDENT 与所有权。非所有者返回与不存在一致的404，管理员/教师不隐式获取私人草稿。
- 请求不得设置 owner、发布状态、奖励、审核字段；额外字段拒绝。响应只提供管理草稿所需字段，不返回 owner/学号/联系资料。URL/API 的资源 UUID 为路由引用，页面不显示内部标识。
- 更新携带预期 version，数据库原子条件更新确保并发保存只成功一次；冲突409，提示刷新并保留用户未保存输入。事务由服务控制，创建/更新提交成功后才报告保存成功。
- 创建采用 UUID request_id 幂等键（owner+request_id 唯一），防止网络重试重复建立草稿。相同键与不同内容冲突409；相同内容重试返回既有草稿，不能覆盖后续编辑。

## 页面

个人中心增加“我的项目草稿”入口，管理页与现有学生布局、设计 token、表单、错误状态保持一致。显示“仅自己可见”的边界，不出现无功能的发布/审核按钮，不设置人才/导师空页面。

列表覆盖加载、为空、错误；编辑表单带 label、长度提示、就地错误、保存中/成功反馈。已保存与未保存状态区别清楚。新建/编辑/刷新读取均使用真实 API，复用 CSRF fetch。小屏无横向滚动，键盘可用，焦点清晰，状态反馈有可访问提示。

## 测试先行及验收

先从上述规则记录创新域测试矩阵预期，再编写失败用例，随后实现。

1. DTO：空白名称、超长字段、拒绝额外owner/状态字段、可保存未完成草稿。
2. PostgreSQL/API：沿用真实登录与 Bearer 业务请求，新建→重新读取→更新；另一个学生列表不可见，直链读写404；未登录/停用/非学生拒绝；仅 refresh Cookie 不得读取或写入草稿。现有 refresh/logout 的 CSRF 规则保持不变，不为 IE 自创新的认证途径。
3. 独立连接并发更新：同版本仅一个成功，另一409；同幂等键并发创建只有一条；原始创建请求重试返回当前草稿，不覆盖后续编辑；同键不同内容409。
4. 迁移：独立测试库从空库升级至head，新迁移降级再升级，现有本地演示库升级保留账号与旧业务。
5. 前端：交互相关单测、typecheck/lint/check:css；真实浏览器保存、刷新、修改；桌面/手机及短键盘走查。新稳定界面附固定字体视觉基线及选择器契约。
6. API 面变化同步 OpenAPI 快照与生成类型；对新增行为做独立代码审查，修复实质问题后报告本轮实际验证范围。

不运行会清空已有开发数据的全栈重置脚本；测试限专用测试数据库。此闭环可用于本地学习和演示，不等同三库完成或正式上线验收。

## 回归检查中发现的测试同步问题

在本轮 Windows/Node 24 环境，既有 `auth-transition-serialization.test.ts` 的 A 用例稳定失败，B 用例也有同样前置条件缺口：两者称刷新请求已在途，却在 Web Locks 回调实际开始之前就触发登录/退出。生产逻辑正确取消尚未开始的旧刷新，导致测试没有进入其声称验证的场景。

仅修测试夹具：等待 REFRESH mock 确实收到请求，再触发登录/退出，保留原有凭证隔离、请求顺序及次数断言；补 B 的次数断言，避免 `indexOf=-1` 造成假通过。不修改认证生产代码或禁用 Web Locks。该问题已在完整单测与独立文件中复现，修复后重跑两者并独立审查。
