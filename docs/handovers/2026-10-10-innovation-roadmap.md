## 1. 项目目标与资料边界

学姐负责既有校园任务众包部分；用户负责同一 CampusQuest 仓库中的创新创业部分，可自主规划，拿不准的业务事项再询问学姐。当前建设项目库、人才库、导师库，首要目标是集中展示校内双创成果，其次是项目招募、学生实践机会和导师查找。第四库不属于当前开发与验收。

依据：

- 工作区《华师令创新创业板块独立需求说明书.docx》v0.7：业务来源，只有标为“已明确”的内容是文档需求基线，建议和待定内容不能自动成为交付承诺。
- 工作区《华师令创新创业板块技术实现文档.md》：技术参考，尚未核实的仓库假设以实际代码为准；其原成果更新免复审方案已被本次用户决定覆盖。
- 工作区《华师令CampusQuest 需求说明书（SRS）.pdf》：原校园任务业务来源，不把任务的随机分配、数据提交和积分规则搬到双创项目。
- 仓库细化设计、相关实施计划和质量文档：实现约束；用户当前明确决定优先。外部技能不改变业务范围。

项目、人才、导师的关键规则已有足够信息，可以分批推进；完整 demo 边界、激励数值、学校认证及正式上线参数仍不够明确。不能据此宣称“全需求已精确定义”。

## 4. 后续入口与层级：目标示意

```text
华师令主导航
├─ 既有首页 / 任务 / 排行榜 / 积分奖励 / 通知
├─ 创新创业
│  ├─ 板块首页：成果优先，随后有效招募；三库入口
│  ├─ 项目库 → 项目详情 → 成果 / 团队 / 招募 / 授权联系
│  ├─ 人才库 → 人才详情 → 优势 / 意向 / 状态 / 授权联系
│  └─ 导师库 → 导师详情 → 方向 / 成果 / 接收状态 / 授权联系
├─ 我的
│  ├─ 原个人档案与账户设置
│  ├─ 负责人资料与资格
│  ├─ 我的项目 → 项目管理 → 成果 / 招募 / 成员与授权
│  └─ 我的人才档案 → 维护 / 预览 / 展示开关
├─ 双创运营工作台（仅获授权者）
│  └─ 审核待办 / 后续内容治理、导师维护等按职责开放
└─ 账号区域 → 我的 / 退出登录

ADMIN 的资格开通与运营授权仍属于管理后台。
```

逻辑是按“找资源—维护自己的资源—处理运营任务”分入口。看校内成果无需先知道个人中心结构；写草稿、维护联系方式与公开展示分开，防止误公开。运营工作台独立可达，但菜单可见并不能替代后端权限。教师等已有校内角色也应能进入获准浏览范围，不因学生侧边栏整合而失去访问路径。

首页表现、手机导航和精确菜单分组需复用仓库设计系统。手机优先、电脑兼容属于文档要求；视觉大幅重做与品牌色尚不是已确认范围。

## 6. 一两周 demo 与完整交付：工期建议

没有正式 demo 验收清单，也没有已完成的新规则详细设计，因此下面只能是初步区间。不能用学生每天 1–1.5 小时乘几天，直接推导 AI 能完成多少全栈功能；代理运行、独立检查、环境故障与用户验收各自占时间。

**建议目标：10–14 个自然日形成可现场演示的核心三库版本。** 它应具备可用的基本视觉与手机操作，内容可以模拟，但核心业务真实执行。功能正确和基本可用性都要保证；不把“前端未优化”理解为按钮不可达、手机溢出、权限漏露或缺失状态提示。

| 建议时间窗口 | 优先推进 | 该窗口结束时展示什么 |
| --- | --- | --- |
| 第 1–3 天 | R1 + R2，R0 远端问题穿插调查 | 入口清楚、能退出、成果每次更新审核与旧版保留 |
| 第 4–6 天 | R3，准备有成果/仅招募两类示例 | 项目库中展示成果、发布招募、查看授权联系和岗位状态 |
| 第 7–9 天 | R4 | 人才库可浏览、本人建档、公开/关闭、联系与基本筛选 |
| 第 10–12 天 | R5 的核心确认/授权链路 | 导师库中测试档案从未确认到确认展示，方向与授权联系可用 |
| 第 13–14 天 | R9 集成、缺陷修复、演示彩排 | 负责人、运营、浏览者及必要导师测试角色能走完整脚本 |

此安排是**建议的核心 demo 范围，尚非用户签字确认的缩减范围**。R6、R7、R8 仍属总规划；若学校所说“demo”必须连共同管理、转让、完整举报治理、四类激励都能操作，不能承诺以上时间表。按这些额外闭环及验证工作，建议为完整双创业务版本先预留约 3–5 周，从本检查点起算，学校认证和校方资源等待另计；此区间同样需要阶段完成后重估，不是保证。

已有权限、历史不可变、文件安全和适用质量门禁不得为压缩工期删减。第 3 天用已完成 R1/R2 的真实耗时重估；第 7 天再核对人才/导师剩余量。若落后，报告具体缺口与新的可演示范围，再由用户决定，不私自把未做功能换成假按钮。

用户每天建议安排：10–15 分钟看本轮目标和决定，20–30 分钟按验收卡操作，15–20 分钟理解一项与项目相关的知识，其余时间反馈和讨论。一个工作包可能跨多个聊天轮次/多天，不要求每次消息都交付一个完整模块。

[官方模型说明](https://learn.chatgpt.com/docs/models) 推荐 Sol 用于复杂及持续工作，Luna 用于清楚、重复的任务；Medium 平衡速度与深度，High 适合困难的多步推理。下面路由是项目判断，仍保留用户原默认 Sol High，采用其他设置前说明理由和本轮验收。

| 工作性质 | 建议模型/强度 | 升级或保持高强度的条件 |
| --- | --- | --- |
| 跨文档规划、成果复审、公开字段边界、状态机、迁移 | Sol High | 本项目核心风险；不要因代码量少自动降档 |
| 已明确设计的常规列表/表单、导航布局、提示文案 | Sol Medium | 一旦涉及身份切换、受限缓存、权限不变量或新规则，回 High |
| 格式整理、已核实字段的结构转换、小范围明确文案 | Luna High，可选 | 不独立决定业务；不承担跨域审核/账本变更；无需为一条小改动强制换模型 |
| 跨角色验收设计、真实 PG 并发、疑难环境/CI 问题 | Sol High | 无需日常 Max/Ultra；反复失败先定位证据而非不断升强度 |
| 重大独立评审、认证迁移或复杂账本争议 | 按评审技能和风险选最强合适模型，必要时 Astra | 不常驻；具体模型与额度影响先说明，遵守实际评审要求 |

“Sol”代际要按用户选项确认；官方当前推荐 GPT-6.1 Sol，并不构成擅自把用户正在使用的其他 Sol 换成 6.1。主聊天设置由实际客户端选择决定，助手不能声称已经自动切换。

建议优先使用 Standard 速度。官方说明同一模型 Fast 消耗订阅额度约为 Standard 的 2.5 倍；新开聊天不会重置账户共享额度。额度受模型、上下文、推理、工具与缓存影响，不能按 prompt 条数或字符数可靠预测。[官方额度说明](https://learn.chatgpt.com/docs/pricing)

成本管理建议：

1. 每完成一个工作包记录前后使用比例和实际产出，积累本项目样本后再估剩余量；不承诺固定节省百分比。
2. 将阶段目标与代码定位保存在文档，避免在同一长聊天中重复读全仓与重做已确认设计；必要规范阅读照常保留。
3. 预留约四分之一的计划资源用于回归、评审与修复，这是管理缓冲，不能把账户的 64% 精确切成 token 包。
4. 重置卡留作连续开发真的受限且临近 demo 的缓冲；普通额度仍允许时不先消耗。使用前让用户看到实际限制与替代选择，不能自动兑换。
5. API 作为持续受限时的候选补充，届时按官方价格、计费方式和实际调用样本制定金额上限；本轮不购买、不配置付费调用、不假定订阅和 API 共用余额。
6. 不默认开启多个代理。确有适用技能要求的独立评审才按规则安排；不会把安装了多代理技能当成全程并行授权。

DeepSeek V4.1 Flash 在本项目尚未完成可用性、工具兼容及质量实测，没有证据说它可以等质量替代 Sol。建议当前主线先保持已工作的执行环境；如要比较，另做一个边界明确的可逆小任务，比较实际修改、测试、人工修正与总成本后再决定。此处不对未核验模型做能力/价格排名。

## 8. 新对话：何时开、带走什么、如何续接

建议在本规划保存后开一个新的项目聊天，仍使用同一仓库、同一分支。本轮达到自然边界：上一轮成果闭环已体验，用户对更新规则和入口给了新决定；老聊天含较多历史、旧免复审设计和工具日志。新聊天的价值是减少混淆、明确当前工作包，不是重置额度。

一个聊天围绕一个可验收工作包，不必每条消息新开。出现以下情况再续接：阶段交付且验收完成；切换业务域；当前聊天频繁丢失确认事项或反复找旧日志；用户需要独立的教学讨论。没有可以可靠报告的“当前上下文百分比”，不能凭对话看着长就断言剩余 token。

每次结束至少补全：本轮目标、用户新增决定及其范围、已实现/未实现、分支和最新提交、验证日志与对应 head、人工验收结果/未做步骤、已知缺陷、下一步、阻塞与需要谁决策。源码的 Git 保存与规划文档是两回事，都需说明；只写摘要不等于代码已提交。

新聊天先读本文件，再按任务读历史续接和相关设计/计划；不要把旧摘要“更新免复审”或“下一步直接招募”当最新授权。不要复制所有旧聊天进首条 prompt，也不自动 fork 全部历史。不要自动归档旧聊天，它仍是确认记录的来源。

建议首轮负责 R1 的设计落地与实施计划，适用范围明确后再执行；R2 在下一工作包处理，不为了省聊天同时包进三库全量开发。R0 的 CI 状态调查可穿插进行。

## 9. 谁负责决定、谁负责执行、如何保证符合需求

代理负责：核对文档与代码，制定本轮具体方案，按适用要求实现、测试、评审和保存；处理能自己定位的环境/CI问题；准备可执行的验收卡。不能用“测试通过”代替业务符合性。

用户负责：决定模糊的业务选择和优先级、体验每批可观察结果、指出不符合使用习惯的地方、确认面向学校的演示范围。不要求用户为了参与而手动重复代理能可靠完成的终端操作。

学姐/业务负责人需要决定或协助提供：学校品牌/校徽规范；首期辅助功能组合；演示必须包括的完整功能；真实运营职责和首批资料；积分完善条件、分值、徽章、贡献核实和推荐周期；培训活动实际资源。第四库事项不阻塞前三库。之前已确认的资格方案、模拟账号、成果更新规则不重复问。

学校接口/运维负责人：SSO 协议和身份字段、绑定迁移及失效策略、材料保留/配额、预计规模、备份恢复目标、正式环境与责任人。SSO 实现排最后，不等于假定届时无需等待接口。

CI：目前用户无需再做一次授权或学习流水线命令。代理先核对具体 run、head、job 与失败/未运行原因；只有证据表明确需上游维护者批准运行时，才给用户准确页面和可转发请求。已解决的推送权限不再当作学姐要决定的问题。

每个工作包交付一张验收卡：需求来源/用户决定 → 谁操作 → 从哪里进入 → 操作 → 应看到什么 → 不应出现什么 → 证据。覆盖正常路径、拒绝/失败路径与公开权限。实际完成后将需求逐行对应实现与测试，标明仅建议/待配置项目；不能把广义“其他没问题”扩大成全需求签字。

技术验证按 `campusquest-test-process` 和仓库门禁选择：开发中先针对性检查，阶段结束跑适用门禁，新增接口同步契约工件，数据库行为用真实 PG，前端检查手机/桌面、键盘/无障碍与规定视觉基线。检查失败后修复再验证，不降标准强行通过；不因未改代码而机械重跑全部套件。完整 CI 与独立评审须对准同一最终 head。

Git 建议沿用现有 feature 分支，每个可解释工作包做聚焦提交并推到已授权 fork，更新 Draft PR 描述和交付证据；是否拆更多 PR 依据审查规模/上游协作决定。保持现有开发数据，不重置工作区、不改 main、不自动合并。

## 10. 用户干中学的最小路线

| 随哪个阶段学 | 应能理解/说出来的内容 | 直接用本项目练 |
| --- | --- | --- |
