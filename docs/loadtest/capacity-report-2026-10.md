# CampusQuest 首次容量报告（2026-10）

Spec: `docs/superpowers/specs/2026-09-29-load-testing-design.md` ·
方法: 容量估算 → 场景即代码 → 正确性断言（见 ADR 0001）

## 一句话结论

单机形态下，系统在 **50 并发提交者**目标负载上零错误零丢失通过全部正确性
断言（API 腿 P99 1.64s）；**300 人抢 60 名额零超发**、全部落败者拿到 §8.4
稳定业务码；容量战役挖出一个生产级并发缺陷——**上传意向流的数据库死锁**
（证据留档，移交专属修复 PR）。

## 目标与估算（面试讲稿的起点）

学校 ~3 万人 → 一门 1000 人报名的大课作业 → 拖延定律让最后 10 分钟挤进
~100 人 → 现实在途并发 ~10–20，**目标按 50 并发打**（留余量），崩溃点由
递增腿实测。

## 环境与 SUT 形态（诚实声明）

- 单机：uvicorn `--workers 2` + 1 Celery worker + beat；PostgreSQL 16 /
  Redis 7 / MinIO（`infra/docker-compose.yml` + loadtest overlay，慢查询
  日志 200ms）
- 单 locust 进程（同机）；API 级压测（不经浏览器渲染）
- **登录容量未测**（设计决定）：每 IP 每小时 50 次的登录限流使单源压测
  不可能；套件用种子期离线铸 token（与登录同一 `issue_session` 路径）
- 本机磁盘全程 98% 满——它本身就是第一道容量天花板（见发现 2）

## 结果矩阵（每行数字都由 `backend/loadtest/runs/` 留存工件支撑）

| 场景 | 负载 | 结果 | P99（API 腿） | 正确性检查 |
|---|---|---|---|---|
| S1 截止抢交（目标） | 50 并发 / 4.5 min | 55 提交（含版本化重交）全成功，0 错误 0 限流；踩点小组按时开火 | 1.64 s | ✅ check_s1：零丢失/零重复/§9.3 分档 oracle 全对；排水 max 21.4s / mean 9.1s |
| S1 递增（修复前口径） | 100 并发 | 1 次 500（死锁，见发现 1） | ~2.7 s | ⚠️ 该两轮递增的 summary 工件被当时的固定 run 目录 bug 覆盖销毁（审查 I2，已修复为每次独立目录）；死锁证据完整留存于 `stack-logs/uvicorn.log` |

（401/403/404）与传输失败（连接重置，locust status=0）一律记**错误**——
这正是审查挖出的分类学缺陷（C1/I7），修复后才有了本表的诚实数字。

## 发现（按重要度）

1. **上传意向流死锁（生产级，移交修复）**：100+ 并发下
   `POST /submissions/upload-intent` 偶发 PostgreSQL
   `DeadlockDetectedError` → 500。锁图（留存于 `stack-logs/uvicorn.log`
   与 PG 日志摘录）：intent 流的 `SELECT ... FOR UPDATE`（claim 行）与
   验证 worker 的裸 `UPDATE assignment_claims SET status='UNDER_REVIEW'`
   相互等待——worker 绕过了 upload_service 文档规定的
   user→claim→intent 锁序。慢查询日志佐证：竞争窗口内 claim 行
   UPDATE 996ms、FOR UPDATE 290ms。**修复属产品正确性变更，需专属 TDD PR**
   （确定性并发复现 + 锁序对齐），不在本容量 PR 内夹带。
2. **磁盘是单机形态的第一道天花板**：200 并发时 MinIO 卷 52 秒被
   ~30MB 级上传打爆（桶内还堆着 3.2GB 历史残留——retention=DAYS_180，
   压测期间无人清理）。容量规划必须把"对象存储增长率"与 QPS 一起算；
   压测桶应定期清理。
3. **写路径 P99 随并发的劣化曲线**（1.6s@50 → ~2.7s@100 → ~7.9s@200）：
   主导因素是 claim 行锁竞争 + 大文件 PUT 带宽分享。可观测性（B 方向）
   落地后应给出按端点的分解。

## 与第一版报告的差异（审查修正）

审查发现初版报告三处数字无工件支撑/口径错误：排水 7.7s 实为 5 用户
dry-run 的数；"err 6.3%"与工件算出的 8.1% 不符；"0 错误"漏计了 1 次被
误分类为成功的连接重置。本版全部数字来自修复后重跑的留存工件，递增腿
的历史数字标注了工件已毁的事实。

## Phase-2 展望（CI 性能预算）

本报告数字即预算基线：S1@50 的 API 腿 P99 1.64s、S2 的 60/300 胜负比与
码白名单、check 全绿。下一步以覆盖率棘轮同样的哲学做成 `perf-ratchet`
（劣化即红）。
